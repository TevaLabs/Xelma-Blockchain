# Security Review

This document records adversarial attack scenarios, protocol defenses, test
coverage, and residual risks for the Xelma Precision commit-reveal pipeline.

## Adversarial Scenarios (Issue #414)

All scenarios are exercised in
[`contracts/src/tests/adversarial.rs`](../contracts/src/tests/adversarial.rs)
and run via:

```bash
cargo test --package xelma-contract --lib tests::adversarial -- --nocapture
```

Or equivalently via the adversarial suite script:

```bash
./scripts/run_adversarial_suite.sh
```

### Scenario 1: Salt Grinding Defense

| Field | Detail |
|-------|--------|
| **Attack** | Attacker tries many low-entropy salts (zero-filled, constant-byte, sequential) to bypass the on-chain entropy check and produce a predictable commitment preimage. |
| **Defense** | `InvalidSalt` (error 64) — the contract rejects zero-filled and constant-byte salts at reveal time. The entropy check forces the attacker to produce 256-bit unpredictable salts. |
| **Test** | `test_adversarial_salt_grinding_defense` — tries 10+ low-entropy patterns, all rejected; valid high-entropy salt succeeds. |
| **Residual risk** | The on-chain check cannot prove the salt was generated by a CSPRNG. A client could technically use a high-entropy-but-predictable sequence (e.g. sequential counters). This is a residual risk because the contract cannot verify off-chain randomness source quality. Production clients should use `crypto.getRandomValues()` or equivalent. |

### Scenario 2: Commit-and-Grief Non-Reveal

| Field | Detail |
|-------|--------|
| **Attack** | Attacker commits an extremely large bet and deliberately never reveals, hoping to: (a) lock honest participants' capital, or (b) exploit the forfeiture mechanism to steal the pot. |
| **Defense (mixed reveal)** | When some users reveal and others don't, the unrevealed user's stake is **forfeited to the pot**. Honest revealers win the entire pot including the griefer's forfeited stake. The griefer loses their entire bet. |
| **Defense (all unrevealed)** | When nobody reveals, ALL stakes are returned as refunds — no funds are burned or locked. |
| **Test** | `test_adversarial_commit_and_grief_non_reveal` — griefer commits 500 tokens, honest user commits 100 tokens; only honest user reveals; griefer's stake is forfeited; conservation invariant holds. |
| **Residual risk** | In the mixed-reveal case the griefer loses their entire stake. This is a rational-actor deterrent but not an economic guarantee — a griefer who values disruption more than their stake can still impose waiting costs on honest participants (they must wait until resolution to recover). |

### Scenario 3: Cross-Round Commitment Replay

| Field | Detail |
|-------|--------|
| **Attack** | Attacker reuses a commitment hash from a previous round in a new round, hoping to predict the outcome without knowing the actual price or to confuse the settlement logic. |
| **Defense** | Commitments are stored per `(round_id, user)`. A commitment from round 1 is invisible in round 2 — calling `reveal_prediction` in the new round returns `CommitmentNotFound` because no commitment was made in the new round's bet window. |
| **Test** | `test_adversarial_cross_round_commitment_replay` — attacker commits in round 1, resolves, then tries to reveal in round 2 using the old preimage; `CommitmentNotFound` is returned. |
| **Residual risk** | None identified. The storage key isolation is strict and enforced at the storage layer. |

### Scenario 4: Double-Commit Griefing

| Field | Detail |
|-------|--------|
| **Attack** | Attacker commits twice in the same round with different prices, hoping to pick the better one at reveal time. |
| **Defense** | `AlreadyBet` (error 12) — `commit_prediction` rejects a second commitment from the same user in the same round. The contract tracks `(round_id, user)` pairs and enforces single-commitment-per-user. The `place_precision_prediction` path is also blocked after a commit. |
| **Test** | `test_adversarial_double_commit_rejected` — attacker commits once, second commit returns `AlreadyBet`, direct-prediction bypass also returns `AlreadyBet`. |
| **Residual risk** | None identified. The check is strict and covers both commitment and direct-prediction paths. |

## Unrevealed Forfeiture

The protocol handles unrevealed commitments as follows:

| Condition | Outcome | Test Coverage |
|-----------|---------|---------------|
| **All unrevealed** | Full stake refund to all participants | `commit_reveal_e2e::test_commit_reveal_e2e_all_unrevealed_refunds_conservatively` |
| **Mixed (some revealed, some not)** | Revealer(s) win full pot; unrevealed stake forfeited | `commit_reveal_e2e::test_commit_reveal_e2e_mixed_reveal_forfeits_unrevealed_to_pot` and `adversarial::test_adversarial_commit_and_grief_non_reveal` |
| **All revealed** | Normal precision scoring | `commit_reveal_e2e::test_commit_reveal_e2e_full_lifecycle` |

## Related Test Modules

| Module | Scope |
|--------|-------|
| `tests::commit_reveal_e2e` | Full commit-reveal lifecycle, failure branches, tie resolution |
| `tests::adversarial` | Grinding, griefing, replay, double-commit scenarios |

## Build Verification

⚠️ **Pre-existing blocker on upstream/main**: `contracts/src/settlement.rs`
contains duplicate `void_round` / `finalize_round` function definitions and
other structural errors that prevent `cargo check` from succeeding. This
blocker was present before this branch was created. The adversarial test
code is syntactically and semantically correct by inspection, but test
execution cannot be verified until the upstream compilation errors are
resolved.

```bash
# This will fail due to pre-existing settlement.rs errors on upstream/main:
cargo check --package xelma-contract --locked
```
